## Алхам 1 — Локал API

`local-server/server.js`-т гурван endpoint байна:

| Endpoint     | Зан төлөв                            | Зорилго                       |
| ------------ | ------------------------------------ | ----------------------------- |
| `POST /cart/add` | ~1-5 мс дотор `{ok:true}` буцаана | Performance SLO-ийн бай       |
| `GET  /report`   | 200-400 мс санамсаргүй хүлээлт     | Латентын дээд хязгаарыг харна |
| `POST /pay`      | ~5% магадлалтай `500` буцаана     | Reliability SLO-ийн бай       |

Ажиллуулах: `cd local-server && node server.js` — `API: http://localhost:3000`.

## Алхам 2 — 3 чанарын сценарио (6 хэсэгтэй формат)

Лекц 3-ын форматаар: **Тойм · Системийн төлөв · Орчны төлөв · Гадаад өдөөлт · Шаардлагатай хариу · Хэмжүүр**.

### Сценарио 1 — Performance (`/cart/add` хариу хугацаа)

| Хэсэг              | Утга                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| Тойм               | Хэрэглэгч бүтээгдэхүүнийг сагсанд нэмэхэд түр саатал үзэхгүй байх                                          |
| Системийн төлөв    | API ажиллаж байгаа, `/cart/add` endpoint 200 OK буцаах чадвартай                                              |
| Орчны төлөв        | 20 VU зэрэгцэн ажиллах хэвийн үдийн peak ачаалал (~15 iter/s ≈ 45 req/s)                                    |
| Гадаад өдөөлт      | Хэрэглэгч "Сагсанд нэмэх" товч дарж POST хүсэлт илгээнэ                                                       |
| Шаардлагатай хариу | Хүсэлтийн 95% нь 200 мс-ээс бага хугацаанд `{ok:true}` буцах                                                  |
| Хэмжүүр            | `http_req_duration{name:cart}` **p(95) < 200 мс**, 1 минутын цонхонд                                          |

### Сценарио 2 — Reliability (`/pay` эвдрэлийн давтамж)

| Хэсэг              | Утга                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| Тойм               | Төлбөрийн үйлдэл тогтмол амжилттай явагдах, gateway-ийн санамсаргүй алдаа хүлцэх хязгаараас гарахгүй байх |
| Системийн төлөв    | `/pay` endpoint ажиллаж байгаа, төлбөрийн gateway-тэй холбогдож байгаа                                        |
| Орчны төлөв        | 20 VU 1 минутын турш төлбөр хийж байна                                                                        |
| Гадаад өдөөлт      | Хэрэглэгч төлбөрийн товч дарна (POST /pay)                                                                    |
| Шаардлагатай хариу | Нийт хүсэлтийн 92%-аас олон нь 200 OK байх (өөрөөр хэлбэл алдаа 8%-аас бага)                                  |
| Хэмжүүр            | `http_req_failed{name:pay}` **rate < 0.08**, 1 минутын цонхонд                                                |

### Сценарио 3 — Availability (сервер зогсох ба сэргэх)

| Хэсэг              | Утга                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| Тойм               | Сервер санамсаргүй унасан ч нийт үйлчилгээний availability босго дотор үлдэх                                  |
| Системийн төлөв    | API анх ажиллаж байгаа, дараа нь process нь SIGKILL-ээр устгагдана                                            |
| Орчны төлөв        | 20 VU 2 минутын турш тасралтгүй хүсэлт илгээнэ                                                                |
| Гадаад өдөөлт      | **Эвдрэл (chaos):** t=30с үед сервер устана, 10 секундийн дараа дахин асна                                    |
| Шаардлагатай хариу | Тэст мужын дунд амжилттай хүсэлтийн хувь 90%-аас доош унахгүй байх                                            |
| Хэмжүүр            | `checks` **rate > 0.90**, 2 минутын цонхонд (10 секундийн зогсолттой)                                         |

> **"Сайн сценариогийн 5 шинж"-ээр өөрийгөө шалгав:**
> итгэмжтэй (endpoint-ууд нь бодит систем шиг зан төлөвтэй) · үнэ цэнэтэй (хэрэглэгчийн туршлагыг хэмжинэ) ·
> тодорхой (босго тоогоор) · нарийн (SLI бүр нэг endpoint-тэй холбогдоно) · ойлгомжтой (5 мөрөнд багтаж байна).

## Алхам 3 — Сценариогоос SLO гаргах

| # | Сценарио      | SLI                              | Босго            | Цонх / нөхцөл                       |
| - | ------------- | -------------------------------- | ---------------- | ----------------------------------- |
| 1 | Performance   | `/cart/add` latency              | **p(95) < 200 мс** | 20 VU, 1 мин                        |
| 2 | Reliability   | `/pay` error rate                | **< 8%**         | 20 VU, 1 мин                        |
| 3 | Availability  | нийт check амжилтын хувь         | **≥ 90%**        | 20 VU, 2 мин, 10с зогсолт орсон     |
| 4 | (нэмэлт)      | `/report` latency                | **p(95) < 450 мс** | 20 VU, 1 мин                        |

**Босго сонгосон үндэслэл:**

- **200 мс** — Nielsen-ийн UX судалгаагаар хэрэглэгч 100-200 мс-ийн доторх хариуг "шууд" гэж мэдэрдэг тул сагсанд нэмэх шиг хурдан үйлдэлд энэ хязгаарыг сонгов. Localhost дээр реал утга нь 1-2 мс байх тул босго нь бодит хэмжигдэхүүнээс тэн доор хамаагүй сул — гэвч энэ нь **регресс илрүүлэх дохио**: хэрвээ ирээдүйд ямар нэг өөрчлөлт үүнийг 200 мс давуулах юм бол шууд FAIL болно.
- **8%** — серверийн кодод `Math.random() < 0.05` буюу 5% алдаа шингээгдсэн тул 8% нь энгийн ажиллагаанд бага зэрэг зай өгсөн бодитой босго. 5% гэж тавибал санамсаргүй хэлбэлзлээс болж хааяа FAIL болно; 10% нь дэндүү сул.
- **90%** — 2 минутын цонхонд ирэх 10 секундийн зогсолтыг тэсвэрлэх зорилготой SLO. Хэрвээ 95% сонговол 10с зогсолт байнга FAIL болгоно; 85% нь дэндүү өршөөнгүй.
- **450 мс (/report)** — серверийн `sleep(200-400 мс)` дээр сүлжээ, TCP handshake зэрэг 50 мс-ийн зайг оруулж тавьсан.

**Error budget (2 минутын Availability цонхонд):**

- **Цагаар:** 2 мин × (1 − 0.90) = **12 секундийн эвдрэх эрх**. Тестийн 10с зогсолт нь энэ доор багтаж байна.
- **Хүсэлтээр:** ~5700 нийт хүсэлтийн 10% = **570 хүсэлтийн эрх**. Гэвч бодит эвдрэл болсон үед 765 хүсэлт унасан (доор Алхам 5-ыг үз) — цагаар багтсан ч хүсэлтээр хэтэрсэн. **Хоёр тоо яагаад зөрж байгааг Алхам 5-д тайлбарлав.**

## Алхам 4 — SLO-г k6 threshold болгох (PASS хувилбар)

`slo-test.js` — endpoint бүрд `name` tag тавьж, threshold-ыг tag тус бүрд бэхлэв:

```js
export const options = {
  vus: 20, duration: '1m',
  thresholds: {
    'http_req_duration{name:cart}':   ['p(95)<200'],  // Performance SLO
    'http_req_duration{name:report}': ['p(95)<450'],  // 4-р (нэмэлт) сценарио
    'http_req_failed{name:pay}':      ['rate<0.08'],  // Reliability SLO
    'checks':                         ['rate>0.90'],  // Availability SLO
  },
};
```

Ажиллуулсан команд:

```bash
k6 run slo-test.js 2>&1 | tee results/pass.txt
```

**Гаралт:** [`results/pass.txt`](results/pass.txt) · exit code = **0**

| Threshold                          | Босго       | Хэмжсэн утга | Төлөв |
| ---------------------------------- | ----------- | ------------ | ----- |
| `http_req_duration{name:cart}`     | p(95) < 200 | **1.49 мс**  | ✓ PASS |
| `http_req_duration{name:report}`   | p(95) < 450 | **388.98 мс**| ✓ PASS |
| `http_req_failed{name:pay}`        | rate < 0.08 | **4.61%**    | ✓ PASS |
| `checks`                           | rate > 0.90 | **98.46%**   | ✓ PASS |

Нийт: 2796 хүсэлт (45.66 req/s), 932 iteration, 43 pay-ийн алдаа. README-ийн бүх тоо `results/pass.txt`-д байгаа.

## Алхам 5 — Chaos: availability сценариог бодитоор турших

Тестийг `duration: '2m'` болгож ажиллуулаад, дунд нь серверийг SIGKILL-ээр устгаж 10 секундийн дараа дахин асаав.

**Timeline:**

| Цаг    | Үйлдэл                              |
| ------ | ----------------------------------- |
| t=0с   | k6 эхлэв (20 VU, 2m)                |
| t=30с  | `kill -9 <server-pid>` — сервер зогслоо |
| t=30-40с | Downtime — /cart, /report, /pay бүгд `ECONNREFUSED` |
| t=40с  | `node local-server/server.js` — сервер сэргэв |
| t=120с | k6 дууссан                          |

Ажиллуулсан команд:

```bash
k6 run slo-test.js 2>&1 | tee results/chaos.txt   # duration=2m хувилбартай ижил скрипт
```

**Гаралт:** [`results/chaos.txt`](results/chaos.txt) · exit code = **99** (FAIL)

| Threshold                          | Босго       | Хэмжсэн утга | Төлөв |
| ---------------------------------- | ----------- | ------------ | ----- |
| `http_req_duration{name:cart}`     | p(95) < 200 | **1.37 мс**  | ✓ PASS |
| `http_req_duration{name:report}`   | p(95) < 450 | **389.53 мс**| ✓ PASS |
| `http_req_failed{name:pay}`        | rate < 0.08 | **16.36%**   | ✗ FAIL |
| `checks`                           | rate > 0.90 | **86.57%**   | ✗ FAIL |

**Бодит availability (хүсэлтээр тооц):**

```
availability = амжилттай хүсэлт / нийт хүсэлт
             = 4935 / 5700
             = 86.57%
```

**Error budget:**

- Цагаар: 12с эрх байсан, 10с зарцуулсан → **цагаар багтсан**.
- Хүсэлтээр: 570 хүсэлтийн эрх байсан, 765 хүсэлт унасан → **195 хүсэлтээр хэтэрсэн**.

**Хоёр тоо яагаад зөрж байна вэ?**
k6-ийн VU нь `sleep(1)` хийж iteration хийдэг. Хэвийн үед нэг iteration ~1.3с (нэг /report-ын 300 мс + бусад). **Гэвч сервер унасан үед `ECONNREFUSED` шууд буцаж ирдэг тул /report-ын 300 мс алга болно** — iteration нь ~1.05с болж хумигдана. Иймд downtime секунд бүр хэвийн секундээс **~24% олон хүсэлт "иддэг"**. Тиймээс 10 секундийн зогсолт нь хүсэлтээр 12 секундийн budget-ыг хэтрүүлсэн.

**Reliability threshold мөн FAIL болсон уу — яагаад?**
Тийм. `http_req_failed{name:pay}` нь 4.61% (PASS run)-с 16.36% (chaos)-руу үсэрсэн. Учир нь: downtime үед /pay-ийн бүх хүсэлт connection refused буцаадаг — нэг эвдрэл нь **availability ба reliability SLO хоёуланг зэрэг зөрчсөн**. Энэ бол сайн SLI дизайны хичээл: reliability-г availability-с тусгаарлахын тулд *"сервер асаалттай байх үед"* гэсэн нөхцөл нэмэх (жишээ нь HTTP 5xx-г ялгах, connection error-ыг оруулахгүй) хэрэгтэй.

## Алхам 6 — Threshold-оо зориуд эвдэх

`slo-test-fail.js` — /report-ын threshold-ыг **p(95) < 100 мс** болгов. Серверийн код 200-400 мс хүлээдэг тул энэ нь **ямар ч машин дээр найдвартай FAIL** болдог.

/cart/add-ын threshold-ыг **p(95) < 50 мс** болговч энэ нь **localhost дээр PASS хэвээр үлдэнэ**. Учир нь localhost ping ~1-2 мс, 50 мс нь бодит утгаас 25 дахин илүү сул. Энэ бол лекцийн жишээ: "PASS болгохын тулд бус, сценариодоо бодитой байхаар" босго тавих.

Ажиллуулсан команд:

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=$?"
```

**Гаралт:** [`results/fail.txt`](results/fail.txt) · exit code = **99**

| Threshold                          | Босго       | Хэмжсэн утга | Төлөв |
| ---------------------------------- | ----------- | ------------ | ----- |
| `http_req_duration{name:cart}`     | p(95) < 50  | **1.73 мс**  | ✓ PASS |
| `http_req_duration{name:report}`   | p(95) < 100 | **387.67 мс**| ✗ FAIL |
| `http_req_failed{name:pay}`        | rate < 0.08 | **4.62%**    | ✓ PASS |
| `checks`                           | rate > 0.90 | **98.45%**   | ✓ PASS |

k6-ийн гаралтын сүүлд:

```
time=... level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
```

**Exit code 99** — CI pipeline (GitHub Actions, GitLab CI, Jenkins) яг энэ тэг биш утгыг мэдэрч build-ыг зогсоодог. Хэрвээ 0 буцаасан бол PR merge болох байсан.

## Дүгнэлт

Сценариос SLO руу шилжих алхам хамгийн хэцүү нь **босгыг зориудаар шийдэх** үе байлаа. Ялангуяа /cart/add-ын p(95)<200 мс нь localhost дээр 1.5 мс байхад "утгагүй сул" мэт харагдсан ч, регрессийн дохио болох үүргээ гүйцэтгэдэг гэдгийг Алхам 6-ын PASS хариу баталсан — 50 мс болгож бууруулахад ч энэ нь бодит рүү ойртсонгүй. Reliability босгыг 8% гэж тавьсан нь серверт 5% алдаа шингээсэн бодит утгыг харгалзсан бөгөөд PASS run-д 4.61%, chaos run-д 16.36% гарсан нь босгын мэдрэмжийг зөв тохируулсныг харууллаа. Chaos туршилт нь availability сценариогийн хэмжүүрийг **үгүйсгэсэн** — 10 секундийн зогсолт цагаар 12 секундийн budget-т багтсан ч, хүсэлтээр 570 → 765 хэтэрсэн тул SLO зөрчигдсөн. Энэ зөрүүг олж харах явцад k6-ийн `checks` метрикын мөн чанар (цагаар биш хүсэлтээр) тодорхой болов. Хамгийн гэнэтийн олдвор нь reliability threshold бас FAIL болсон явдал — нэг crash хоёр SLO-г нэгэн зэрэг унагадаг тул reliability SLI-г availability-с тусгаарлах шаардлагатай болохыг харлаа. Threshold-ыг зориудаар эвдэх алхам нь CI-ийн exit code (99) яагаад build-ыг зогсоодог механизмыг гардан харуулж, "тестийн үр дүн код руу шингэсэн шаардлага" гэж лекцэд заасан ойлголтыг батлав. Ерөнхийдөө: сценарио → SLI → босго → threshold шугам нь "хүсэлт биелж байна уу" гэсэн субъектив асуултыг автоматаар шалгагдах бодит тоо болгож хувиргах хөшүүрэг юм. Ирээдүйд бодит production-д ийм threshold-ыг PR-т суулгавал регресс мержийг ил гаргах чадвартай.
