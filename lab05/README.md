## Тест дизайн (Лекц 5-ын 5 алхам)

### Алхам 1 — Бие даан тестлэгдэх функц

`POST /registrations` — оюутныг хичээлд бүртгэх. Оролт: `studentID`, `courseID` + серверийн төлөв (оюутан, хичээлийн бичлэг). Төлөвийг `PUT /students/:id`, `PUT /courses/:id` setup хүсэлтээр бүрдүүлнэ.

### Алхам 2-3 — Сонголтууд ба төлөөлөх утгууд

| #   | Сонголт (parameter / environment)         | Эквивалент анги              | Төлөөлөх утга                                   |
| --- | ----------------------------------------- | ---------------------------- | ----------------------------------------------- |
| C1  | `studentID`-гийн хүчинтэй байдал          | идэвхтэй                     | `status: "active"`                              |
|     |                                           | идэвхгүй                     | `status: "inactive"`                            |
|     |                                           | байхгүй                      | PUT хийгээгүй ID (`S2_NOBODY`)                  |
|     |                                           | талбар дутуу _(хязгаар)_     | body-д `studentID` байхгүй                      |
| C2  | Оюутны үзсэн хичээлүүд (`coursesTaken`)   | урьдчийг хангана             | `["CS201"]`                                     |
|     |                                           | урьдчийг хангахгүй           | `["CS100"]`, `[]`                               |
|     |                                           | хоосон _(хязгаар)_           | `[]`                                            |
| C3  | `courseID`-гийн хүчинтэй байдал           | байгаа                       | PUT хийсэн `CS313`                              |
|     |                                           | байхгүй                      | PUT хийгээгүй ID (`S4_NOCOURSE`)                |
|     |                                           | талбар дутуу _(хязгаар)_     | body-д `courseID` байхгүй                       |
| C4  | Хичээлийн урьдач нөхцөл (`prerequisites`) | бүгдийг үзсэн                | `["CS201"]` ⊆ coursesTaken                      |
|     |                                           | огт үзээгүй                  | `["CS201"]`, coursesTaken = `["CS100"]`         |
|     |                                           | заримыг нь үзсэн             | `["CS101","CS201"]`, coursesTaken = `["CS101"]` |
|     |                                           | урьдач нөхцөлгүй _(хязгаар)_ | `[]`                                            |
| C5  | Хүсэлтийн формат                          | зөв JSON                     | `{"studentID":…, "courseID":…}`                 |
|     |                                           | буруу JSON _(хязгаар)_       | `{"studentID": "…", "courseID": `               |

**Боломжгүй / утгагүй хослолууд:** оюутан _байхгүй_ бол C2 (үзсэн хичээлүүд) тодорхойлогдохгүй; хичээл _байхгүй_ бол C4 (урьдач нөхцөл) тодорхойлогдохгүй; _буруу JSON_ бол C1–C4 бүгд утгагүй. Тиймээс бүрэн декарт үржвэр (3×2×2×3 = 36) биш, доорх стратегиар сонгосон.

### Алхам 4 — Спецификациуд (лекцийн стратеги: happy path 1 + алдааны анги бүрд 1 + давхар алдаа + хязгаар)

| #   | Ангилал                     | Оюутан (C1, C2)       | Хичээл (C3, C4)             | Хүлээгдэх статус | Хүлээгдэх `result`                          |
| --- | --------------------------- | --------------------- | --------------------------- | ---------------- | ------------------------------------------- |
| S1  | Happy path                  | идэвхтэй, `["CS201"]` | байгаа, `["CS201"]`         | **201**          | `OK` + `registrationID` тоо                 |
| S2  | Алдаа: оюутан               | байхгүй               | байгаа, `["CS201"]`         | **200**          | `ERROR_NO_STUDENT`                          |
| S3  | Алдаа: оюутан               | идэвхгүй, `["CS201"]` | байгаа, `["CS201"]`         | **200**          | `ERROR_INACTIVE_STUDENT`                    |
| S4  | Алдаа: хичээл               | идэвхтэй, `["CS201"]` | байхгүй                     | **200**          | `ERROR_NO_COURSE`                           |
| S5  | Алдаа: урьдач (огт үзээгүй) | идэвхтэй, `["CS100"]` | байгаа, `["CS201"]`         | **200**          | `ERROR_PREREQUISITES`, `missing: ["CS201"]` |
| S6  | Алдаа: урьдач (зарим нь)    | идэвхтэй, `["CS101"]` | байгаа, `["CS101","CS201"]` | **200**          | `ERROR_PREREQUISITES`, `missing: ["CS201"]` |
| S7  | Давхар алдаа                | идэвхгүй, `[]`        | байгаа, `["CS201"]`         | **200**          | `ERROR_INACTIVE_STUDENT` (давамгайлна)      |
| S8  | Давхар алдаа                | байхгүй               | байхгүй                     | **200**          | `ERROR_NO_STUDENT` (давамгайлна)            |
| S9  | Хязгаар                     | идэвхтэй, `[]`        | байгаа, `[]` (урьдачгүй)    | **201**          | `OK` + `registrationID` тоо                 |
| S10 | Хязгаар                     | идэвхтэй              | `courseID` талбар дутуу     | **400**          | `ERROR_BAD_REQUEST`                         |
| S11 | Хязгаар                     | —                     | буруу JSON                  | **400**          | `ERROR_BAD_JSON`                            |

Давхар алдааны (S7, S8) хүлээгдэх утгыг зааварт заагаагүй тул тестээр тогтоосон: сервер **оюутан → идэвхтэй эсэх → хичээл → урьдач нөхцөл** дарааллаар шалгадаг.

### Алхам 5 — Бодит тест кейс

Спецификаци бүр [`lab05-collection.json`](lab05-collection.json)-д тусдаа **folder** болсон: өөрийн setup `PUT`-ууд → `POST /registrations` → oracle-ууд.

**Тест бие даасан байдал (Лекц 4):** тест бүр өөрийн гэсэн давхцахгүй ID (`S1_…`, `S2_…`) ашиглаж setup-аа өөрөө хийдэг тул дангаар нь эсвэл ямар ч дарааллаар ажиллуулж болно. `registrationID` сервер ажиллах хугацаанд хуримтлагддаг тул oracle нь яг утгыг биш, **тоо эсэхийг** л шалгана (`to.be.a("number")`).

## Даалгавар 4 — Newman-ы үр дүн

```bash
newman run lab05-collection.json 2>&1 | tee results/newman-pass.txt
echo "exit=${PIPESTATUS[0]}"
```

| Ажиллуулалт                | Collection                   | requests (executed / failed) | assertions (executed / failed) | Exit code | Гаралт                                               |
| -------------------------- | ---------------------------- | ---------------------------- | ------------------------------ | --------- | ---------------------------------------------------- |
| **PASS**                   | `lab05-collection.json`      | 26 / 0                       | **26 / 0**                     | **0**     | [`results/newman-pass.txt`](results/newman-pass.txt) |
| **FAIL**                   | `lab05-collection-fail.json` | 26 / 0                       | 26 / **1**                     | **1**     | [`results/newman-fail.txt`](results/newman-fail.txt) |
| **DOWN** (сервер унтарсан) | `lab05-collection.json`      | 26 / **26**                  | 26 / **26**                    | **1**     | [`results/newman-down.txt`](results/newman-down.txt) |

**Тестийн тоо:** 11 тест (folder / test-script), **26 assertion** — `results/newman-pass.txt`-ийн `assertions │ 26 │ 0` мөртэй яг таарна.

- **FAIL:** `AssertionError Статус 200 — expected response to have status code 200 but got 201`. Newman 1-ээр гарсан нь CI pipeline-ийг зогсоох **quality gate** болно: нэг ч oracle унавал build амжилтгүй.
- **DOWN:** гаралтад `connect ECONNREFUSED 127.0.0.1:3000` мөр байна.
  **Ялгаа:** ECONNREFUSED бол _интерфейсийн алдаа_ — хүсэлт серверт хүрээгүй, хариу огт ирээгүй тул системийн зан төлөвийн талаар юу ч хэлэхгүй; харин FAIL-ийн _oracle-ийн алдаа_ нь сервер хариу өгсөн боловч хүлээгдэж буй утгатай таарахгүй байгааг (согог эсвэл буруу oracle) илтгэнэ.

## Дүгнэлт

Дизайны 5 алхмаас хамгийн их бодол шаардсан нь **2-3-р алхам — сонголтуудыг тодорхойлж эквивалент ангид хуваах** байсан, учир нь функцийн оролт зөвхөн `studentID`, `courseID` хоёр ч бодит зан төлөв нь серверийн _төлөвөөс_ (оюутны статус, үзсэн хичээл, урьдач нөхцөл) хамаардаг тул далд сонголтуудыг илрүүлэх хэрэгтэй болсон. Урьдач нөхцөлийг "бүгд / огт үгүй / заримыг нь" гэж гурав хуваасан нь `missing` массив зөвхөн дутуу хичээлийг буцааж байгааг (S6) шалгах боломж олгосон. Боломжгүй хослол олон таарсан: оюутан байхгүй бол түүний үзсэн хичээл, хичээл байхгүй бол түүний урьдач нөхцөл гэдэг ойлголт утгагүй, буруу JSON бол бусад бүх сонголт утгаа алддаг. Иймээс 36 хослолын бүрэн үржвэрийн оронд happy path + алдааны анги бүрд нэг + давхар алдаа + хязгаар гэсэн стратегиар 11 спецификацид хүрсэн. Давхар алдааны үед аль нь буцахыг заавар тодорхойлоогүй байсан тул S7, S8 тестээр сервер оюутан → статус → хичээл → урьдач нөхцөл дарааллаар шалгадгийг тогтоосон. Тест бүрд давхцахгүй ID өгснөөр тестүүд бие биеэсээ хамааралгүй, дарааллаас үл хамааран давтан ажиллах боломжтой болсон. Тестүүд серверт _функционал согог_ илрүүлээгүй — 26 assertion бүгд PASS. Гэхдээ дизайны явцад тодорхойлолтын цоорхой ажиглагдсан: `status`-д ямар ч утга (жишээ нь `"ACTIVE"`) өгвөл идэвхгүй гэж тооцогдох, мөн нэг оюутныг нэг хичээлд давхар бүртгэхийг сервер хориглодоггүй бөгөөд энэ нь бодит системд согог байж болох юм. FAIL ба DOWN ажиллуулалт нь Newman-ы exit code-оор oracle-ийн алдаа ба интерфейсийн алдааг хоёуланг нь CI quality gate болгон барьж чадахыг харуулсан.
